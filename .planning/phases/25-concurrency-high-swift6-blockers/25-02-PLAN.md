**WebSocketService.swift — CONC-02:**

In `handleConnection(_:sessionId:projectPath:on:)` (line ~20-40), the `ws.onText` closure on line 28 already uses `[weak self]`. However, the inner `Task` on line 30 captures `ws` (Vapor's WebSocket type) which may not be Sendable. The `ws.onClose` handler on line 35 also spawns a Task.

Current code:
```swift
ws.onText { [weak self] ws, text in
    guard let self = self else { return }
    Task {
        await self.handleMessage(text, sessionId: sessionId, projectPath: projectPath, ws: ws)
    }
}
```

The issue: Inside the `ws.onText` closure, `self` is captured weakly (good), but the `Task` closure captures the `ws` parameter and passes it to `handleMessage`. In Vapor, `WebSocket` is a class that conforms to `Sendable` (it's an actor-like type), so this is actually safe. However, to be defensive and match the audit finding:

Fix approach: The `ws` parameter in the `onText` callback IS the same WebSocket — Vapor provides it as a convenience. Since WebSocketService is an actor and `ws` is already stored in `connections[sessionId]`, we can retrieve it from there instead. But simpler and correct: Vapor's WebSocket IS Sendable (it uses NIOLockedValueBox internally). So the real fix here is to verify the capture is safe and add a comment documenting why.

Actually, looking at the audit finding H-C2 more carefully: "WebSocket `ws.onText` Task strong self" — the concern is that the Task captures `self` strongly after the `guard let self` unwrap. Fix: use `[weak self]` on the Task itself too, OR since `self` is already weak-unwrapped in the outer closure, pass needed values explicitly.

The cleanest fix:
```swift
ws.onText { [weak self] ws, text in
    guard let self else { return }
    Task { [weak self] in
        guard let self else { return }
        await self.handleMessage(text, sessionId: sessionId, projectPath: projectPath, ws: ws)
    }
}
```

This ensures the inner Task also holds a weak reference to self, preventing retain cycles if the WebSocket outlives the service.

Apply the same pattern to `ws.onClose`:
```swift
ws.onClose.whenComplete { [weak self] _ in
    Task { [weak self] in
        await self?.removeConnection(sessionId)
    }
}
```

**ClaudeExecutorService.swift — CONC-10 / SWIFT6-01:**

On line 62: `static var useAgentSDK: Bool = true`

This is a mutable `static var` on an actor. The `nonisolated func execute()` on line 115 accesses it via `Self.useAgentSDK` (line 120). Under Swift 6 strict concurrency, a mutable static var on an actor cannot be accessed from a nonisolated context — this is a compile-error blocker.

Fix options (from audit):
1. `nonisolated(unsafe) static var` — marks the static as explicitly unprotected. Acceptable because this is a configuration flag set once at startup and read many times. No data race in practice.
2. `nonisolated static let` — if the value never changes at runtime, make it a constant.
3. `@TaskLocal static var` — thread-local storage.

The value CAN change (user could toggle SDK vs CLI mode), so option 1 is correct:

```swift
/// When true, uses the Agent SDK (via Node.js wrapper) instead of `claude -p`.
/// The SDK calls the Anthropic API directly, avoiding the subprocess hang issue.
/// Set to false to fall back to `claude -p` when running outside Claude Code.
///
/// `nonisolated(unsafe)` is safe here: this flag is set once during app configuration
/// (before any concurrent access) and read many times. No concurrent writes occur.
nonisolated(unsafe) static var useAgentSDK: Bool = true
```

This is the standard Swift pattern for configuration flags that are set-once-read-many and eliminates the Swift 6 compile error.
