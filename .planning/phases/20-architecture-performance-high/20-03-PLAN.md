**ProcessListView (UIPERF-03):**
`classifyProcess()` (line ~169) is called per row in ForEach. It does multiple `.contains()` string checks for each process name. With 50 displayed processes, this runs 50x per body evaluation.

Fix by pre-computing classifications:
1. Add `@State private var classificationCache: [String: ProcessBadge] = [:]` to ProcessListView (or to the ViewModel if one exists — check `viewModel.filteredProcesses`).
2. When `viewModel.filteredProcesses` changes, compute classifications for all visible processes in a single pass:
   ```swift
   .onChange(of: viewModel.filteredProcesses.count) { _, _ in
       var cache: [String: ProcessBadge] = [:]
       for process in viewModel.filteredProcesses.prefix(50) {
           cache[process.name] = classifyProcess(process.name)
       }
       classificationCache = cache
   }
   ```
3. Also populate in `.task` on initial load (same logic).
4. In `processRow()`, replace `classifyProcess(process.name)` with `classificationCache[process.name]`.
5. Keep `classifyProcess()` as a private helper (used only during cache population).

Fix:

2. The import is triggered by a `.fileImporter` result handler. Wrap the file reading in a `Task {}`:
   ```swift
   Task {
       let jsonData = try Data(contentsOf: fileURL)
   ```

**DashboardViewModel (SPERF-04):**
`loadAll()` (line ~42) calls `loadStats()` and `loadRecentActivity()` sequentially:
```swift
await loadStats()
await loadRecentActivity()
```
These are independent API calls that can run in parallel.

Fix:
1. Replace the sequential calls with `async let`:
   ```swift
   async let statsResult: Void = loadStats()
   async let recentResult: Void = loadRecentActivity()
   _ = await (statsResult, recentResult)
   ```
2. Both functions write to different @Observable properties (stats vs recentSessions), so parallel execution is safe from a data perspective.
3. However, since DashboardViewModel is @MainActor, both functions will be serialized on the main actor anyway due to actor isolation. To get true parallelism, the network calls would need to happen off-actor. Since APIClient is an actor itself, the `try await client.get(...)` calls already run on the APIClient actor — the parallelism comes from not waiting for one to finish before starting the other.
4. If `async let` within a @MainActor class does not achieve parallelism, use `withTaskGroup`:
   ```swift
   await withTaskGroup(of: Void.self) { group in
       group.addTask { await self.loadStats() }
       group.addTask { await self.loadRecentActivity() }
   }
   ```
5. Either approach is fine — the key is both network requests are in flight simultaneously.

**ChatMessage (SPERF-03):**
ChatMessage is a struct with 11 stored properties including arrays (`toolCalls`, `toolResults`) and optional Strings. During streaming, each token appends to `text` and creates a full struct copy.

Optimization approach — reduce copy cost:
1. ChatMessage already has a custom `==` that checks all 11 fields. During streaming, only `text` changes. Add a `mutating func appendText(_ newText: String)` that modifies text in-place. This does not eliminate the copy (it is a value type in an array), but makes the intent clear.
2. More impactful: In ChatViewModel, if streaming updates only modify the last message's text, use index-based mutation instead of creating a new array:
   - Check ChatViewModel for how it updates messages during streaming.
   - If it uses `messages[lastIndex].text += token`, that is already optimal for value types (in-place mutation via subscript).
   - If it replaces the entire message (`messages[lastIndex] = updatedMessage`), that is a full copy.
3. Document the finding: ChatMessage is 11 fields but only ~200 bytes per instance (2 UUIDs, 1 Bool, 2 Strings, 2 small arrays, 2 optionals, 2 numbers). The copy cost is dominated by String CoW — which Swift handles efficiently via copy-on-write. Add a code comment documenting this analysis.
4. If the arrays `toolCalls` and `toolResults` are typically empty during streaming, the copy cost is minimal. Add `@inline(__always)` to the `appendText` method if created, or simply add a doc comment explaining why struct is acceptable.

**SPERF-02 (any AppTheme) documentation:**

The remaining `any AppTheme` usage in ThemeManager.swift and ThemeMarketplaceView.swift is by design (theme registry must store protocol existentials to support custom themes). // SPERF-02: `any AppTheme` here is by design — the theme registry stores heterogeneous

