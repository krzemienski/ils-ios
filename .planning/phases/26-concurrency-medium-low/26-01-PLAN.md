    **CONC-03: ProjectsViewModel.swift line 67** — Replace `Task.detached { await CacheService.shared.cacheProjects(data.items) }` with plain `Task { await CacheService.shared.cacheProjects(data.items) }`. The Task.detached is unnecessary because:
    - ProjectsViewModel is @MainActor
    - CacheService is an actor
    - The call `await CacheService.shared.cacheProjects(...)` already hops to the CacheService actor
    - Task.detached needlessly escapes MainActor isolation for no benefit
    - This matches the pattern already applied in DashboardViewModel (line 72, comment C-MED-5) and SessionsViewModel (line 241, comment C-MED-6)
    Add a comment: `// CONC-03: Use Task instead of Task.detached — CacheService actor handles isolation.`

    **CONC-06: SubscriptionManager.swift lines 77-83** — The init currently spawns two Tasks immediately inside init(). While [weak self] prevents crashes, the Tasks could theoretically run before all stored properties are set in a more complex scenario. Restructure to:
    1. Keep the init body minimal — just set stored properties
    2. Create a new `func startListening()` method that contains both Task spawns (the transaction listener and the initial status check)
    3. Call `startListening()` at the END of init after all properties are initialized
    4. This makes the init order explicit: properties first, then async work
    The actual Task bodies remain the same — [weak self] + listenForTransactions/checkSubscriptionStatus/fetchProducts.
    Add comment: `// CONC-06: Tasks deferred to startListening() to ensure full initialization first.`

    **CONC-12: LowPowerModeMonitor.swift line 19** — Replace `nonisolated(unsafe) private var observer: NSObjectProtocol?` with a safe alternative. The current comment says "accessed in deinit" — but for a @MainActor singleton, deinit only runs at process exit. The fix:
    1. Remove `nonisolated(unsafe)` qualifier
    2. Keep `@ObservationIgnored` (observer is not UI-observed)
    3. Change to: `@ObservationIgnored private var observer: NSObjectProtocol?`
    4. Mark deinit as `nonisolated` is NOT needed — @MainActor classes can access stored properties in deinit since they run on the actor
    5. Actually, in Swift 5.10, deinit of @MainActor class runs nonisolated. So wrap the deinit body: store observer in a local `let obs = observer` and remove outside actor. OR simpler: since this is a singleton that never deallocates, just remove the deinit entirely and document why.
    Best approach: Remove the deinit entirely. Add comment: `// CONC-12: No deinit needed — singleton lives for process lifetime. Observer removed automatically at exit.` Remove `nonisolated(unsafe)` from the observer property.

    **CONC-13: AppLogger.swift** — Two Task.detached usages:
    1. **Line 39 (flush timer)**: `Task.detached(priority: .utility)` — This IS the correct pattern. AppLogger is `Sendable` (not actor-isolated), so Task.detached is not escaping any actor. However, since AppLogger is not @MainActor, a plain `Task` would also work and inherit no actor context. Replace with `Task(priority: .utility)` for consistency. Add comment: `// CONC-13: Plain Task — AppLogger is Sendable, no actor isolation to escape.`
    2. **Line 168 (recentLogs)**: `Task.detached(priority: .userInitiated)` — This reads a file from disk. Since `recentLogs` is an `async` method with no actor isolation, `Task.detached` is technically fine but unnecessary. Replace with a simple inline read since we are already in an async context with no actor to block. Change from `return await Task.detached(priority: .userInitiated) { ... }.value` to just execute the file-reading code inline (it is already async and not on any actor). Add comment explaining the file read is intentionally synchronous within this non-isolated async context.
