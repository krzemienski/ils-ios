**MacChatView.swift:**

The rename alert handler (around line 74-78) has:
```swift
Button("Rename") {
    Task {
        let _: APIResponse<ChatSession> = try await appState.apiClient.renameSession(id: session.id, name: renameText)
    }
}
```
And the delete alert handler (around line 84-89) has:
```swift
Button("Delete", role: .destructive) {
    Task {
        let _: APIResponse<String> = try await appState.apiClient.delete("/sessions/\(session.id.uuidString)")
        dismiss()
    }
}
```

Both issues: (1) `try await` inside a bare `Task {}` with no `do/catch` — errors are silently swallowed, (2) direct `apiClient` calls bypass any ViewModel state management.

Fix the rename handler:
```swift
Button("Rename") {
    Task {
        do {
            let _: APIResponse<ChatSession> = try await appState.apiClient.renameSession(id: session.id, name: renameText)
        } catch {
            AppLogger.shared.error("Failed to rename session: \(error.localizedDescription)", category: "macChat")
        }
    }
}
```

Fix the delete handler:
```swift
Button("Delete", role: .destructive) {
    Task {
        do {
            let _: APIResponse<String> = try await appState.apiClient.delete("/sessions/\(session.id.uuidString)")
            dismiss()
        } catch {
            AppLogger.shared.error("Failed to delete session: \(error.localizedDescription)", category: "macChat")
        }
    }
}
```

If `MacChatView` has access to a `SessionsViewModel` (check if it's in @Environment or passed as a parameter), route through it instead of direct apiClient calls. If no ViewModel is available, the `do/catch` with logging is the minimum viable fix — routing through a ViewModel is a Phase 19+ concern when macOS ViewModels are unified.

Also check for any other bare `try await` in Task blocks in the file and add do/catch to each.

**ThemePickerView.swift:**

Line 203 calls `themeManager.availableThemes.contains(where: { $0.id == preview.id })` inside `themeCard()` which is called per card per body evaluation — O(n) per card * 12 cards = O(12n) per render.

Fix: Pre-compute a `Set<String>` of available theme IDs and use O(1) `contains()`:

1. Add a computed property or @State that builds the Set:
   ```swift
   /// Pre-computed set of available theme IDs for O(1) lookup in themeCard()
   private var availableThemeIDs: Set<String> {
       Set(themeManager.availableThemes.map(\.id))
   }
   ```
   If `themeManager.availableThemes` changes rarely (it does — only on app launch or theme install), this computed property is fine. The Set construction is O(n) once per body eval but the per-card lookup becomes O(1).

   Even better: use a `@State` with `.onChange(of:)` if ThemeManager's availableThemes is observable. But since ThemeManager uses @Observable, a computed property that reads `themeManager.availableThemes` will only trigger re-computation when that array changes — which is the correct behavior.

2. In `themeCard()` (line 203), replace:
   ```swift
   let isAvailable = themeManager.availableThemes.contains(where: { $0.id == preview.id })
   ```
   with:
   ```swift
   let isAvailable = availableThemeIDs.contains(preview.id)
   ```

3. Also check line 84 which filters `themeManager.availableThemes.filter { $0.id.hasPrefix("custom-") }`. This is fine as-is (runs once, not per card).

**configure.swift:**

Lines 79-81 set `PRAGMA foreign_keys = ON` via a raw SQL query after `autoMigrate()`. This only affects the current connection — in a connection pool, new connections won't have FK enforcement.

Fix: Set the PRAGMA via SQLite's connection configuration callback so it runs on every new connection in the pool:

1. Replace the current database configuration (line 58-59):
   ```swift
   let dbPath = app.directory.workingDirectory + "ils.sqlite"
   app.databases.use(.sqlite(.file(dbPath)), as: .sqlite)
   ```
   with a configuration that includes the PRAGMA in the connection setup. Fluent's SQLite driver supports this via `SQLiteConfiguration`:
   ```swift
   let dbPath = app.directory.workingDirectory + "ils.sqlite"
   var sqliteConfig = SQLiteConfiguration(storage: .file(path: dbPath))
   sqliteConfig.enableForeignKeys = true
   app.databases.use(.sqlite(sqliteConfig), as: .sqlite)
   ```
   Check Fluent's SQLiteConfiguration API — if `enableForeignKeys` is available, use it. If not, use the lower-level approach:
   ```swift
   app.databases.use(DatabaseConfigurationFactory.sqlite(.file(dbPath), sqliteConfiguration: .init(foreignKeys: true)), as: .sqlite)
   ```
   The exact API depends on the FluentSQLiteDriver version. Check `Package.resolved` for the version and use the appropriate API.

   If neither built-in option exists, use the pool configuration callback approach:
   ```swift
   app.databases.use(.sqlite(.file(dbPath), connectionPoolTimeout: .seconds(10)), as: .sqlite, isDefault: true)
   ```
   And set up a middleware or lifecycle handler that runs `PRAGMA foreign_keys = ON` on each request. But the cleanest approach is the SQLiteConfiguration method.

2. Remove the old PRAGMA block (lines 78-81):
   ```swift
   // Enable foreign key constraints on the SQLite connection
   if let sqlDB = app.db as? SQLDatabase {
       try await sqlDB.raw("PRAGMA foreign_keys = ON").run()
   }
   ```
   And update the comment to explain the new approach.

3. Verify by checking the FluentSQLiteDriver source or docs. The key requirement: `PRAGMA foreign_keys = ON` must execute on EVERY connection the pool creates, not just the first one.
