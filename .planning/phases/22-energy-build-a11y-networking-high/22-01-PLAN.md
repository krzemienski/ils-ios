## Task 1: PulsingGlow + PulsingModifier — onDisappear stop (ENRG-04)

**Problem:** PulsingGlow and PulsingModifier start `.repeatForever()` animations on `onAppear` but never stop them on `onDisappear`. Views off-screen (e.g., scrolled away, tab switched) continue animating, wasting GPU cycles.

**Fix in `ILSApp/ILSApp/Theme/CyberpunkEffects.swift`:**

### PulsingGlow (lines 34-66):
Add `@State private var isVisible = false` property.

Add `.onDisappear`:
```swift
.onDisappear {
    isVisible = false
    withAnimation(.linear(duration: 0.1)) {
        isAnimating = false
    }
}
```

Change `.onAppear` to set `isVisible = true` before starting animation.

Change `.onChange(of: scenePhase)` active branch to also check `isVisible`:
```swift
if newPhase == .active, isVisible {
```

### PulsingModifier (lines 76-118):
Same pattern — add `@State private var isVisible = false`.

Add `.onDisappear`:
```swift
.onDisappear {
    isVisible = false
    isAnimating = false
}
```

Change `.onAppear` to set `isVisible = true`.
Change `.onChange(of: scenePhase)` active branch to check `isVisible`.

## Task 2: SSE background disconnect (ENRG-05)

**Problem:** SSEClient stays connected when the app enters background, keeping the radio active and draining battery.

**Fix in `ILSApp/ILSApp/Services/SSEClient.swift`:**

SSEClient is `@MainActor @Observable`. It needs to observe `scenePhase` changes. However, SSEClient is a service (not a view), so it can't read `@Environment(\.scenePhase)`.

**Approach:** Add a `handleScenePhase(_ phase:)` method to SSEClient. The view layer (ChatView) already manages scene lifecycle and can call this.

Add to SSEClient:
```swift
/// ENRG-05: Disconnect SSE when app backgrounds to save battery.
/// Called by view layer's scenePhase observer.
func handleAppBackgrounded() {
    guard isStreaming else { return }
    streamTask?.cancel()
    streamTask = nil
    connectionState = .disconnected
    // Don't clear messages or error — preserve state for resume
}
```

But wait — SSEClient streams are request-initiated (user sends a chat), not persistent connections. Let's verify:
- If the user backgrounds mid-stream, the stream should be cancelled to save battery.
- The user can re-send when they foreground.

Actually, re-reading SSEClient, it has `stopStreaming()` method. The ChatView should call `sseClient.stopStreaming()` on scenePhase change to background.

**Fix:** In ChatView.swift (or ChatMessageList.swift), the scenePhase observer should call `sseClient.stopStreaming()` when backgrounded during active streaming. But ChatView is modified heavily in other phases.

**Simpler fix:** Add a NotificationCenter observer in SSEClient init for `UIApplication.didEnterBackgroundNotification`:
```swift
// In init():
#if os(iOS)
NotificationCenter.default.addObserver(
    forName: UIApplication.didEnterBackgroundNotification,
    object: nil,
    queue: .main
) { [weak self] _ in
    Task { @MainActor [weak self] in
        guard let self, self.isStreaming else { return }
        self.stopStreaming()
        // ENRG-05: Cancel active SSE stream on background to save battery radio.
    }
}
#endif
```

This is self-contained in SSEClient — no view changes needed.
