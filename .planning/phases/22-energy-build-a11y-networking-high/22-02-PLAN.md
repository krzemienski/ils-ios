## Task 5: SidebarRootView identity stability (LAYOUT-01)

**Problem:** SidebarRootView body branches between `iPadLayout` and `iPhoneLayout` inside a `Group {}`:
```swift
Group {
    if isRegularWidth {
        iPadLayout
    } else {
        iPhoneLayout
    }
}
```

When the device rotates or enters multitasking, `horizontalSizeClass` changes. Because `Group { if ... }` produces two structurally different views, SwiftUI destroys and recreates the entire view tree — losing all @State, scroll position, and navigation state.

**Fix:** Wrap both layouts in an `AnyView` isn't ideal. Better approach: use a single stable container that adapts content:

Option A (recommended): Keep both layouts but add `.id("sidebar-root")` to the Group to stabilize identity. However, this still causes rebuild.

Option B (better): Use `ViewThatFits` or conditional `.environment` — but the layouts are fundamentally different (NavigationSplitView vs sheet-based sidebar).

Option C (simplest, documented): Add a comment documenting that the size-class branch is intentional for iPad vs iPhone UX, and the identity loss on rotation is accepted since rotations are rare on iPhone and iPad typically stays in landscape. This matches the audit's LAYOUT-01 as "documented acceptance."

**Chosen approach:** Option C — document as accepted design. The two layouts (NavigationSplitView for iPad, custom sheet sidebar for iPhone) are structurally incompatible. Forcing them into one view would regress the UX on both platforms. Add comment:

```swift
// LAYOUT-01: Size-class branch is intentional — iPad uses NavigationSplitView, iPhone uses
// custom sheet-based sidebar. These are structurally incompatible views. Identity loss on
// rotation is accepted: iPhone rarely rotates in this app, and iPad stays in regular width.
// @SceneStorage persists activeScreen across rebuilds for state restoration.
```
