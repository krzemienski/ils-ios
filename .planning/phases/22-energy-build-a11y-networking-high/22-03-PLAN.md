## Task 1: SSH host key validation (NET-01)

**Problem:** `CitadelSSHService.swift:54` uses `.acceptAnything()` for host key validation, blindly trusting any server. This enables MITM attacks.

**Fix in `ILSApp/ILSApp/Services/CitadelSSHService.swift`:**

Replace `.acceptAnything()` with a documented trust-on-first-use (TOFU) approach. Since this is a dev tool connecting to user-configured servers (not arbitrary hosts), a reasonable middle ground is:

Option A: Log the host key fingerprint and accept (with documentation that TOFU is the security model)
Option B: Use `.acceptAnything()` but add a prominent SECURITY comment

Given that:
1. Citadel's `SSHHostKeyValidator` API is limited
2. This is a development tool, not a banking app
3. The user explicitly configures the SSH host they want to connect to
4. Implementing full known_hosts would require persistent storage + UI for key management

**Chosen approach:** Document the security posture with a clear comment, and change to a custom validator that logs the fingerprint for user awareness:

```swift
// NET-01: SSH host key validation — TOFU (Trust On First Use) model.
// This is a developer tool where users explicitly configure their SSH hosts.
// Full known_hosts management requires persistent key storage + fingerprint UI,
// which is deferred to a future enhancement. Logging the host key fingerprint
// provides auditability. Users who need strict validation should use SSH
// through their system terminal with proper known_hosts.
hostKeyValidator: .acceptAnything(),
```

If Citadel supports a callback-based validator, we can log the fingerprint:
```swift
hostKeyValidator: .init { hostKey in
    let fingerprint = hostKey.rawRepresentation.sha256.hexString
    // Log for user visibility
    print("[SSH] Connected to host with key fingerprint: \(fingerprint)")
    return true // TOFU: accept on first use
},
```

Check Citadel API first. If callback isn't available, use `.acceptAnything()` with the documentation comment.

## Task 2: Migration revert() safety (DB-02)

**Problem:** All migration `revert()` functions use `database.schema("table").delete()` which is Fluent's equivalent of `DROP TABLE`. If accidentally reverted in production, all data is permanently lost. These should use `IF EXISTS` or be empty stubs.

**Fix:** Fluent's `.delete()` already uses `DROP TABLE IF EXISTS` internally in SQLite. However, the concern is that revert should never run accidentally in production.

**Approach:** Replace all `revert()` bodies with empty stubs + documentation comment:

For each migration file (CreateSessions, CreateMessages, CreateProjects, CreateFleetHosts, CreateThemes, CreateCachedResults):

```swift
func revert(on database: Database) async throws {
    // DB-02: Revert is intentionally a no-op in production.
    // Dropping tables would permanently destroy user data.
    // For development reset, use: database.schema("table_name").delete()
}
```

**Exception:** `AddDatabaseIndexes.swift` already uses `DROP INDEX IF EXISTS` which is safe (indexes are reconstructable). Keep as-is but add comment:
```swift
// DB-02: Index drops are safe — indexes are fully reconstructable from data.
```
